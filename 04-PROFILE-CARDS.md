# 04 · PROFILE CARDS

Everything in `assets/` is generated by `scripts/generate-cards.mjs`, committed
into this repo, and referenced by `README.md` as plain files. No third-party
card service is involved, so nothing here breaks when someone else's free tier
expires. Styling follows [03-DESIGN-SYSTEM.md](03-DESIGN-SYSTEM.md); this
document is only about running and changing the generator.

---

## 1 · 🔴 The two that will waste your afternoon

### 1.1 The workflow needs `PROFILE_TOKEN`, not the default token

`secrets.GITHUB_TOKEN` is an installation token **scoped to this repository
alone**. It cannot enumerate the account's other repos, and — this is the part
that costs time — that is not an error. Repositories it cannot see are simply
*absent*. Every card still renders, perfectly, describing a fraction of the
account.

It went unnoticed for days. With the default token the scan saw **28 of 312**
repositories and 2.41 MB of 101 MB, on which **Ruby ranked 6th at 2.06%** and
went on the public profile, while Python — the actual most-used language at
31.9% — did not appear at all.

| | default `GITHUB_TOKEN` | `PROFILE_TOKEN` (classic PAT, `repo` + `read:user`) |
| --- | --- | --- |
| Repositories scanned | 28 | **312** |
| Code | 2.41 MB | **101 MB** |
| Stars | 6 | **21** |
| #1 language | TypeScript 35.1% | **Python 31.9%** |
| Ruby | **2.06%, rank 6** | 0.05%, rank 21 |

⚠️ `repo` scope is required, not optional: only ~70 of the 312 repositories are
public, so `read:user` alone still reports a minority of the account.

The workflow reads `secrets.PROFILE_TOKEN || secrets.GITHUB_TOKEN`, so it keeps
running without the secret — just wrongly. Two guards exist so it cannot go
quiet again:

- The generator prints what it scanned and **warns** when it sees fewer
  repositories than the account has public ones. `public_repos` from the REST
  profile is public data, so it comes back the same whatever token asked, which
  makes it the one reliable yardstick.
- Cards built from the repo scan append `data.scopeNote` to their own subtitle —
  `⚠ public repos only (28 of 70 scanned)`. A reader should never have to open
  the Actions log to know whether they are looking at a slice.

### 1.2 `USERNAME` is a built-in Windows environment variable

On Windows `process.env.USERNAME` is already set to the **OS account name**, so
running the generator locally silently renders cards for whichever GitHub user
happens to share that name. Always pass it explicitly:

```bash
GITHUB_TOKEN=$(gh auth token) USERNAME=tanghoong node scripts/generate-cards.mjs
```

CI is unaffected — the workflow sets `USERNAME` from `github.repository_owner`.

## 3 · The cards

Declaration order in `cards` **is** README order. It runs most-signal-first:
identity and headline numbers, then "is this person active right now", then
"what do they build with", then the slower shape of the year. The tallest and
most decorative card is last, where its height costs a reader nothing.

| # | Card | Shows |
| - | ---- | ----- |
| 1 | `overview` | Headline stats, active-days ring, top 6 languages |
| 2 | `streak` | Total contributions, current and longest streak |
| 3 | `ability` | Radar over six axes, with the evidence beside it |
| 4 | `activity` | 52 weekly contribution columns |
| 5 | `frameworks` | Squarified treemap, area = repositories using it |
| 6 | `languages` | The whole ranking, share of bytes and repo count |
| 7 | `rhythm` | This year against last, and the weekday habit |
| 8 | `calendar` | Two year-clock dials |

### 3.1 Where the data comes from

Contributions (`streak`, `activity`, `rhythm`, `calendar`) come from
`contributionsCollection`, which is **account-wide and includes private work**
regardless of repo visibility. Those four cards were correct even while the
token was under-scoped — only the three built from the repo scan were wrong.

Frameworks have no GitHub API. They are read out of each repo's dependency
manifests (`package.json`, `requirements.txt`, `pyproject.toml`,
`composer.json`, `Cargo.toml`, `go.mod`), batched 25 repos per aliased GraphQL
query. `gql()` takes `{ partial: true }` there: one unreadable repo in a batch
must not discard the 24 good results beside it.

## 4 · Changing a chart

⛔ **Ask what the number *is* before choosing the mark.** The activity card was
a candlestick twice and both attempts failed for the same reason — contributions
are a **volume**, not a price. A price is a continuously quoted level, so
open/high/low/close are four real observations of one thing; a week's
contributions is a flow, a single number. Forcing four out of it produced:

1. **An artifact.** Priced on a rolling 7-day total, the window double-counted
   every spike — a busy day entered as a green candle and seven days later left
   as a red one of the same height. The chart alternated up/down/up/down through
   the busiest stretch of the year and reported reversals that never happened.
2. **A lie.** Priced as open = the week's first day, close = its last, the week
   of 2026-03-29 — the busiest of its quarter at 158 contributions — drew as the
   **largest loss on the card**, because it opened on a 117-contribution Sunday
   and closed on a quiet Saturday. A 30-contribution week beside it drew green.

A column height cannot invert like that. Both dead ends are written into the
function comment so neither gets walked back into.

### 4.1 Before you ship a chart

- **Take the colour from the ramp.** Never a literal, never a per-language
  identity colour, never a second hue. `t.rampAt(i, n)` for a rank, `t.shadeAt(t)`
  for an intensity — see §4.3.
- **Check it in greyscale.** Render through a `grayscale(1)` filter; anything
  whose meaning lives in colour must survive with no hue at all. This is what
  caught red-vs-green at 1.15:1 — see 03-DESIGN-SYSTEM.md §2.
- **Check both themes.** Light and dark are separate renders, not one with a
  filter.
- **Never let a mark go unlabelled.** The treemap drops its item count until
  every tile can carry its own name, and wraps long names onto two lines. A tile
  showing a bare `1` tells a reader nothing.
- **`assertWellFormed` runs on every write.** A malformed SVG renders as a
  broken image with no error anywhere, so duplicate attributes, unbalanced tags
  and a stray `"` inside an attribute value all fail the build instead.

### 4.2 Previewing locally

There is no test suite; the check is your eyes. Render the assets into a plain
page and screenshot it:

```bash
GITHUB_TOKEN=$(gh auth token) USERNAME=tanghoong node scripts/generate-cards.mjs
# then point any headless browser at a page of <img src="assets/*-light.svg">
```

⚠️ Authoring note: Git Bash on Windows silently eats backslashes and backticks
inside heredocs. Edit `.mjs` and `.md` files with an editor, not with
`cat <<EOF` — it will corrupt regexes and code fences without erroring.

⚠️ And **do not commit what you rendered locally** unless your token is the
full-scope one. A local `gh auth token` typically sees a slice (§1.1), so the
cards it produces are correct-looking and wrong. Preview, then
`git checkout -- assets/` and let CI regenerate them.

### 4.3 The ramp — `scripts/ramp.mjs`

Every data mark is a sample of one ramp, because there is one accent. The
endpoints are the design system's `--c-from` / `--c-to`, and the interpolation
is **in OKLab**:

| | index 0 (the accent) | the tail |
| --- | --- | --- |
| Light | `#03744e` | `#7ee6c3` |
| Dark | `#4dff9b` | `#107f40` |

```bash
node scripts/ramp.mjs 10 --json     # any sample count, either theme
node scripts/ramp.mjs --check       # six samples still equal tokens.css --c-1..--c-6
```

Two interfaces, because cards ask two different questions:

| Call | Question | Used by |
| --- | --- | --- |
| `t.rampAt(i, n)` | **rank** — series *i* of *n* | languages (16), frameworks (n), overview bar, calendar levels |
| `t.shadeAt(t)` | **intensity** — `t` 0 (tail) to 1 (accent) | growth bars, ability bars |

🔴 This was HSL until 2026-09-06, and HSL bunches the steps at one end. The six
dark samples began `#4dff9b #25f981 #0de26a` — three greens nobody can tell
apart. The measurements are in 03-DESIGN-SYSTEM.md §2.2; the short version is a
3–4× spread between the widest and narrowest step, versus 1.03× in OKLab.

⛔ `inkOn()` is a **comparison, not a threshold**. It was `luminance > 0.42`,
which put labels at 2.2:1 in the middle of the ramp. It now asks which of the
two `--accent-ink` values wins and holds 4.40:1 at every sample count. If you
add a card that prints a label inside a filled block, use it — do not re-derive
a cut-off.

`--check` runs in CI before the cards are built, so a well-meaning tidy-up of
the OKLab matrices fails the workflow instead of quietly shifting every colour.

`ramp.mjs` is also the repo's colour module — `luminance`, `contrast`,
`deltaE`, `inkOn` and the two floors live there and are imported by both the
generator and the guard, so the thing being checked is the thing that ships.

### 4.4 The contrast guard — `scripts/contrast.mjs`

```bash
node scripts/contrast.mjs          # report all 40 checks
node scripts/contrast.mjs --fail   # exit 1 on any failure (this is what CI runs)
```

The design system's own `contrast.mjs` parses `tokens.css`, because over there
the stylesheet is the artefact. This repo has no stylesheet: its tokens are
literals inside `generate-cards.mjs` and figures written into
03-DESIGN-SYSTEM.md. So this one reads **both** and fails when they disagree —
with each other, or with the arithmetic. It covers:

| Group | What it asserts |
| --- | --- |
| Accent | Every ratio in §2's table, recomputed; each ≥ AA; the ink is one of the two `--accent-ink` values |
| Ink | `--text`, `--text-2`, `--text-3` on `--bg`, both themes |
| Quiet grey | The `QUIET` block in the doc and in the generator are **the same four hexes**; grey separates from the accent by ≥ 3:1; `edge` still draws the shape when the fill alone is 1.6:1 |
| Ramp | Endpoints match §2.2; the six-sample case clears the ΔE 0.045 legend floor; steps stay within 1.15× of even; monotonic in luminance at 4/6/10/16 (that *is* the greyscale check) |
| Label ink | `inkOn()`'s worst case ≥ 4.40:1 at every sample count, both themes |

🔴 It found real breakage on its first run: §2's closing paragraph claimed
17.4 / 18.1 for `--text`, 4.8 / 5.2 for `--text-3` and 6.4 / 7.1 for the
accent. **None of the six were right** — inherited from an earlier palette,
contradicting the accent table eight lines above them, and read as verified for
a fortnight because nothing recomputed them. A number in prose is a claim
nobody re-checks; that is the whole reason this script exists.

⚠️ When you change a token, the failure tells you both numbers — the computed
one and the documented one. **Fix whichever is actually wrong.** Editing the
document to match a bad colour passes the check and defeats it.

## 5 · Schedule

`.github/workflows/profile.yml` runs daily at 18:00 UTC (03:00 JST), on any push
touching `scripts/**`, and on demand:

```bash
gh workflow run profile.yml --repo tanghoong/tanghoong
```

It commits with `git add -A .`, so **any untracked file left in the working tree
gets swept into a `chore: regenerate profile assets` commit**. Keep the tree
clean, or the next bot run will commit your scratch files for you.
